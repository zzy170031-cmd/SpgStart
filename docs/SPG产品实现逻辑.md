# SPG 产品实现逻辑

## 文档目标

这份文档用于从产品主线、工程结构、数据链路和治理机制四个层面，说明 SPG 当前应如何实现、如何推进、以及如何在关键节点做决策。

它不再把旧四代理文档作为默认治理协议，而是直接对齐现行的 `five-agent-governance`。

## 一句话结论

SPG 当前不是一个“只抓数据”的后端项目，而是一个由以下几层组成的本地产品：

- 桌面壳
- 本机身份门禁
- Provider 配置门禁
- Workbench 主系统
- 内容分析与创作支持
- 五代理治理链

## 1. 当前产品主链路

标准用户路径如下：

1. 启动桌面应用
2. 确认本地用户身份
3. 完成 Provider 保存与测试
4. 解锁主系统 `/galaxy`
5. 在 Workbench 内完成搜索、热点发现、内容拆解、创作指导、选题池沉淀

这个路径说明，SPG 不是“打开即抓取”的工具，而是一个有门禁、有状态、有工作台的产品。

## 2. 现行治理机制

当前主工程的核心研发流程固定接入 `five-agent-governance`。也就是说：

- 需求理解优先走 `Maxwell`
- 结构与实现优先走 `Dirac`
- UI/测试/运维审查优先走 `Parfit`
- 方案整合与两轮质询走 `Wegener`
- 最终反问与裁决走 `Popper`

### 2.1 当前默认规则

- 新项目线程、重大功能、架构变更默认使用五代理启动协议
- `Wegener` 必须完成两轮质询与两轮自审
- `Popper` 必须完成三轮反问与最终五态裁决
- 没有最终裁决，不进入合并或发布判断

### 2.2 为什么不再以四代理为准

旧四代理更接近“多视角协作”，但它把整合与最终放行集中在 `Wegener` 身上。现行五代理把最终门禁独立给 `Popper`，是为了避免：

- 方案整合与放行混在一起
- 需求未锁就提前推进
- 看起来完整、实际仍有关键缺口的假通过

## 3. 工程结构

### 3.1 `spg-core`

负责：

- 游戏实体识别
- 规则归一
- 数据清洗
- SQLite 持久化
- 核心 pipeline 语义

### 3.2 `spg-web`

负责：

- Axum 本地服务
- 页面路由
- Provider 配置与测试
- Workbench API
- 调度与工作台状态

### 3.3 `spg-desktop`

负责：

- Windows 桌面壳
- 本地服务引导
- 托盘与窗口行为
- 加载 `/desktop/launcher`

## 4. 页面与门禁逻辑

### 4.1 入口页

职责：

- 用户进入应用时看到的桌面入口
- 引导进入本地身份确认

### 4.2 身份确认页

职责：

- 确认当前本机用户
- 决定是否允许继续进入 Provider 配置或主系统

### 4.3 Provider 配置页

职责：

- 保存必需 Provider 配置
- 测试是否真实可用
- 作为主系统解锁门禁

### 4.4 Workbench / Galaxy

职责：

- 游戏搜索
- 热点发现
- 视频拆解
- 创作指导
- 选题池沉淀

## 5. 当前 Provider 分工

现行核心 Provider：

- `Doubao`
  - query plan
  - 结构化内容分析
  - 视频拆解
  - 创作建议
- `Serper`
  - 主搜索入口
- `Firecrawl`
  - 正文抓取
- `Tavily`
  - 热点交叉验证
- `Exa`
  - 长尾语义扩展

## 6. 决策与推进规则

### 6.1 应该直接推进的事项

- 已通过五代理前置检查的小型实现
- 已确认方向下的局部修复
- 不改变系统边界的可测调整

### 6.2 应该重新进入治理的事项

- 架构重构
- 主流程变更
- Provider 策略切换
- Sidecar 越界进入主语义
- 合并前与发布前判断

### 6.3 应被阻断的事项

- 仍依赖未确认假设的推进
- 仍存在明显假完整状态的方案
- 仍缺少最终裁决的关键变更
